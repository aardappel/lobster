- Issues where the implementation doesn't follow the spec (docs/source/language_spec.md).
  The spec describes the intended semantics as decided on 2026-09-12; each item says what
  the implementation has to change to catch up, and names the spec section:

  - Integer overflow ("Operators on numbers"): `+ - *` and unary `-` on ints are specified
    to wrap (two's complement), but the generated C does them on signed long long (UB on
    overflow, which a C compiler may exploit), and the constant folder in constval.h does
    the same in C++. Emit them on unsigned long long with casts in CodeGen::BinExpr and
    Unary (and fold them that way), like the shifts already do; check the integer math
    builtins (pow, abs, ...) as well.

- Borrow checker improvements (the visible rules are documented in the spec's "Borrowing"
  section and must stay documented there):

  - "The caller keeps the argument alive" (KeepArgAlive) only resolves conflicts where the
    write happens inside a called function. A write while the borrow is still being
    prepared as an argument of the same call, e.g. `f(v[0], v.pop())`, is an error ("cannot
    modify `v[..]` while `v[0]` borrows it"). Extend the same idea: when a later argument
    writes a location an earlier argument borrows, give the earlier argument an owning
    reference (inc at the borrow, dec after the call) instead of erroring, at the cost of
    one inc/dec at such call sites only.

  - A function value passed as a declared function type has its parameters fixed to
    LT_BORROW (see TypeChecker::SubType for V_FUNCTION), so a lambda body that assigns to
    its own parameter is an error ("cannot assign to borrowed argument"). Lift it by giving
    such a parameter an owning copy on entry when the body assigns it (as ArgLifetime does
    for ordinary calls); the function type's calling convention can stay borrowing at the
    call site.

- constant string caching breaks in-place writes: write_int8_le and friends write into the one
  shared copy of a string constant when it is big enough, so later evaluations of that constant
  see the writes. This prints A, AB, ABC, ..:
    for(10) i:
        var s = "                           "
        s = write_int8_le(s, i, 'A' + i)
        print s
  Same for a string field default used as a buffer (like FlatBufferBuilder's): all objects
  constructed with that default share it.

- `let r = f()` on a function value whose `return` goes to the enclosing function generates C
  that doesn't compile ('p0' undeclared) rather than giving a type error:
    def g():
        let f = fn(): return 1
        let r = f()
        print r
        return 2
    print g()

- flow typing can be subverted in ways that compile and then crash at runtime:
  - a write thru an alias the checker doesn't see, here a `var` that gets reassigned (so it owns
    rather than borrows):
      class Test:
          t:Test?
      let x = Test { Test { nil } }
      var y = x
      y = x
      if x.t:
          y.t = nil
          print x.t.t
  - a call that reuses an already typechecked function doesn't apply that function's demotes
    again (should it, or for now force a specialization if it has demotes?):
      var x:string? = ""
      def f(): x = nil
      if x:  // promoted
          f() // demoted
      x = "abc"
      if x:  // promoted
          f() // nothing happens, f() has already been typechecked
          print x.length
  See also "A more conservative mode" below.

- Borrow checker: writes thru a borrowed parameter (or `this`) are now checked against what
  the callers borrowed or promoted (tests/errors/borrow_param_alias.lobster and friends), and
  vector elements are locations of their own. When the borrow that conflicts is an argument of
  a call, the caller keeps the value alive instead of it being an error (KeepArgAlive). What
  remains unsound is aliasing thru an owning variable that gets reassigned, see the "Detect
  this case" example under "A more conservative mode" below: with `let c = a` it is caught,
  with `var c` that is later reassigned it is not.

- "Functions as environments" is now a specified feature (see declcheck.h): a call to a
  name with no lexically visible function resolves to a local function of that name in
  another scope, valid only while its enclosing function is active (innermost active scope
  wins), mirroring how free variables work. Kept for now because matvoxels relies on it
  (game.lobster's player-update helpers apply_damage/abort_active_item_action/
  show_out_of_stamina/do_deflect are used from 34 call sites in game_item.lobster and
  close over enclosing locals). Revisit whether we want to keep this long term, since
  removing it requires threading those locals as args (or a context object) in such code.

- Dead code checking (TypeCheckDeadCode) covers top level named functions (methods included)
  whose args all have concrete given types. Could be extended to functions with generic args,
  such as methods of generic classes that are never instantiated (checked against their given
  constraints once we have those, see interfaces/traits elsewhere in this file).

- The combination of flow typing upgrades with free variable based specialization often
  causes unexpected issues.
  Typically caused by: a global var foo with a nillable type. foo is used deep down in the
  call-graph. The root of the call graph is called twice, once inside an "if foo" and once
  not, and because it is a free variable causes 2 copies of the entire call graph.
  Besides that, the deep use may give warnings like
  "condition will always succeed with non-nil reference type"
  for one of the copies, which you can't fix because it would error with the other.
  Possible improvements:
  - We could allow a non-nil foo to reuse the nil foo specialization, but we really can't,
    since there may be cases when we want these to compile differently?
    Also, that only works if non-nil compiles first. If its the reverse, we'd have to
    detect this and delete the first specialization somehow :(
  - For the warning, detect that we're in a specialization, ideally specifically that there's
    another specialization where this variable is nil :(
  - (for expert use): we already dump "most clones" on --verbose, but have a quick way to
    dump all specializations of a function too, so we can see what causes the difference.

- "guard" can't be used if there is code following the transformed if-then-else.
  While it is maybe taking things a bit far, you could imagine a guard-finally:

  guard x:
      // The else branch.
  finally:
      // The ending/cleanup code.
  // The main code, which is the then branch.

  Which is equivalent to the familiar:

  if x:
      // The main code.
  else:
      // The else branch.
  // The ending/cleanup code.

  Now this seems like taking things a bit too far, but it could feel logical if the main code
  is really gigantic and the else/ending code is small.
  In theory, it would allow you to get rid of if-then-else entirely, recognizing the idea
  that most code should really be differentiating what is the linear, main line flow from
  the exceptions, though in real code there are cases where the ending code is of course
  the longest.

  And you'd also want a version for guard without else:

  guard x finally:
      // The ending/cleanup code.
  // The main code.

- Weak ref feature.
  we use the informal system of having a "destruct" method on classes that contain members
  causing cycles, and this works well enough to clean up cycles when a tree of objects is deleted in
  one clear place such as end of program or level load, but gets easier to forget to call if
  refs are lost in multiple places.
  We can't detect where to insert these calls automatically because the refc is >= 1
  What if we had a weak ref feature, where backpointers are counted separately, such the decref can
  see when the strong refs drop to 0?
  When strong refs are 0, you'd start the process of deleting, and as that progresses, your weakrefs
  should also drop to 0. If not, it means some of your weakrefs come from objects you don't "own",
  which could be a runtime error.
  Specifically for fields of classes.
  Assigning an object to such a field would only inc the weak refc of that object.
  You'd declare it as part of a field decl:
  class A:
    bs:[B]
  class B
    parent:weak A
  If you do: b.parent = some_other_object_that_is_not_the_parent, then any time that object
  gets cleaned up, it will have a left over weak refc, resulting in a runtime error that at best
  can say: "object of type A has remaining weak refs during destruction".
  That's not the clearest error, but auditing any assignment of "weak" fields with type A should
  be able to narrow it down.
  Harder is: b.parent = A {}, because normally there is no decref to A associated with this code.
  However, since we know we specifically are wanting to inc the weak ref on A, we can also dec
  the strong ref at the same time. That then would instantly trigger deletion, and the same runtime
  error.
  In fact, the runtime side of this feature is pretty much an exchange of a strong ref for a weak
  ref, generated between the value and the weak field it is being assigned to.
  That, and a weak decr for when the field gets overwritten.
  That actually makes it a shockingly simple feature.
  The rest of the language's refc is not complicated either, since it mostly ignores the weak field.
  Biggest deal is the storage of the weak ref field, would not want to add 64-bits to all objects
  for this feature? Would have to maybe efficiently pack these two refc together with ti in 64-bit..
  Problem is, there are realistic scenarios where either refc must be 32 bit.. 16 million objects
  is not that much.
  Or somehow only store it for objects that have weak refs to them.
  It could overlap with the 1st field, and have some metadata for any field iterating code that
  the first field is not a user field.
  Or split up LObject into 2 types, and have field accessors like At() have the correct type generated for them.
  Field iterations code can still use a dynamic offset in the metadata.
  Or maybe better yet, make the pointer to objects point directly at the fields, with normal tti/refc at negative offsets.
  This could have additional speed benefits, though makes access to these fields messier.

  Benchmarking (tests/compare/RESULTS.md) shows C++ mode on par with native C++, but the libtcc JIT
  about 2x slower than C++ mode overall, and up to 7x on raytrace, since libtcc does no inlining and
  little optimisation. MIR (--mir) gets within 1.2x of C++ mode overall, but is still up to 3.4x

  To also get C++ support (so it is easier to share VM code) and Clang level optimisation, you'd
  really need to link all of Clang into Lobster.
  That would make Lobster builds very slow and complicated.
  Instead, what if we used an external Clang to build a DLL?
  More specifically, to not have to deal with the complexity of Clang installs on multiple platforms,
  what if we used Zig? https://zig.news/kristoff/compile-a-c-c-project-with-zig-368j
  This could create another mode, where, if zig is present, it used that instead of libtcc or MIR to
  run during development.
  It would compile the generated code + a few isolated headers, and hopefully such a build could be
  fast enough (within a second?) for development? Run with -O1 or whatever if needed?
  One problem with this path is compatibility with VM code in the main executable.
  VS and Clang compiler at the very least STL containers differently.
  Thus, you'd need to pin building both the main exes for various platforms to always be built with
  a particular version of Clang and the one in the zig exes to the same to have any hope of this
  just working.
  Or rather, only main exes with matching Clang versions would make this path available, you could
  still do VS builds for the better debugging it gives, but they wouldn't have the zig path option.
  If we do get this working, it be a nice option:
  - Do development of programs that require more CPU speed, if builds don't take too long.
  - Could replace the current C++ mode entirely, in that people can just ship main exe + dll,
    with the advantage that they don't have to deal with doing whole project C++ builds.
  - Sets us up on the path of eventually ditching libtcc and MIR, thus not having to deal with C.
    This would really simplify future C++ codegen improvements.
  There is a risk however zig will drop support for C++ compilation: https://github.com/ziglang/zig/issues/16270
  If that happens, this path would have to switch to using a system clang install.
  Frankly, if we implement this path, might as well allow people to choose between zig and a system clang
  install, assuming versions match.
  Other Clang JIT options:
  - https://github.com/hfinkel/llvm-project-cxxjit
    Still requires a whole specialized clang to be linked into the main exe, and would not work with
    dynamically generated code.
  - https://github.com/Kray-G/clang-jit
    Seems like a nice wrapper around clang::CompilerInstance etc, and can do compile+run entirely
    in memory, so could be an option to pre-build this into a .dll separately from Lobster to not

    If this is going to build C++, where is it going to get its STL headers etc from?

- A possible interesting way to optimize our AST storage:
  https://www.youtube.com/watch?v=ZI198eFghJk
  A summary of most of the talk is: do it like the FlexBuffers serializer, build a stack
  of uniform nodes that are then added to a node array contiguously.
  A node can be as small as 64-bit: 32-bit index to children, 24-bit index to per node type infos,
  8-bit type.
  It doesn't seem like the current compiler is bottlenecked by our inefficient ASTs, but we do do
  a lot of cloning and a closed world compile, so it could eventually matter for larger codebases.
  If you assume that these node structs can be overwritten (as part of type checking/optimization),
  but the per-type arrays do not, then cloning becomes even cheaper, only having to copy the
  nodes, if we can guarantee the parser delivers contiguous defs for each function, its a single
  memcpy.
  per-type infos would never be deleted, but nodes could be deleted and reused if desired.
  Biggest huge downside would be the loss of typing of nodes, and having to move from methods
  to a switch.
  You could retain some of the typing by having a Node<E> where E is the enum type such that you
  can statically have Node<T_ADD> even though T_ADD is also stored in the struct?
  Still, will require a lot of casting since there is no automatic upgrade from a generic Node to
  such a type when doing a switch on a Node type.
  Furthermore, for strong typing, you'd want the index to per node type infos to also be strongly
  typed like this, by only allowing indexing with an Index<T_INT> into the array where all integer
  constants are stored, etc.
  It can be done, but is likely a bit of a nightmare to retrofit.
  Better wait for a benchmark of the first huge program that is slow to compile.
  Voxlands of Feb 2024: TIME 0.382 seconds (lobster compile + tcc + program start)
  It is clearly an idea that appeals to my inner optimizer more than there's a need.

- One not so nice thing about `::` to create a type scope is that it forces you to declare the type, e.g.
  hof() x: ..       // don't have to declare type of X, derived from `hof` arg.
  hof() (x::X): ..  // Must declare type.
  hof() (x::): ..   // Type inferred much like above
  hof() (::): ..    // We're not going to use `x`, so should this be possible?
  hof() (_::): ..   // Or just this as a convention.
  Why does this matter? Well this style is awesome for DSLs, where `X` basically brings
  a whole bunch of methods in scope that can be used to construct or render something
  in a very lightweight fashion, where the context (`X`) is implicit.
  `hof` here may be something you want to nest, and the repeated decl of `X` would be unwelcome.
  See: Kotlin, that made a very cool feature out of this:
  https://kotlinlang.org/docs/lambdas.html#function-types

- "guard" is a feature to promote early-out programming style, but more deeply it can also
  be seen as analogous to Icon/ProLog sequence of expressions that can fail.
  It treats a sequence of Lobster statements/exps and says that an exp may fail (0 results)
  thus the statements/exps after it should not be executed.
  But what if you did the same for "success"" of more than 1 result?
  Lobster already has the ability for a function to "generate" results as a HOF and thus
  look like a for loop, which can use a ProLog "cut" operation across function boundaries
  with return, so we can already do this.
  But much like "guard" is a syntax-only feature, you can imagine a flattened version of iteration
  that relies on a HOF or for underneath:
  stat1
  each a = foo(10)
  stat2
  Where "each" is like a "let", except it will iterate the subsequent statements 0..N based
  the values supplied by its initializer.
  "foo" would be a 2-arg HOF where is 2nd arg is the function value implicitly passed, so
  it is equivalent to:
  stat1
  foo(10) a:
    stat2
  If the initializer is not a HOF it would default to the args passed to for, i.e. you could
  write "each a = 10" or whatever.
  "guard" is a special case of this, since you could implement guard as "each _ = boolean_exp"
  I guess additionally "each" doesn't have an optional else block, so the distinction is still
  useful, besides the clear naming.

- A more conservative mode for both flow-upgrades and borrows.
  The current algorithm is "optimistic" in that it doesn't detect all forms of aliasing: it sees
  thru parameters, `this` and variables that borrow what they're initialized with, but not thru
  an owning variable, or any other way code can end up referring to the same object.
  This works well in "real" code as these upgrades/borrows are typically short lived, and
  programmers tend to not access the same data over unrelated aliases.
  However, if we want to be fully sound even just as a check, it be interesting to see what
  is required for it to be impossible to subvert.
  - 1. Aliasing: it will always be possible to obtain two refs to the same data structure
    though independent and complex code that the compiler can't know refer to the same
    object. This means that writes to any type T must invalidate upgrades/borrows of any
    such types, even if under different idents/paths.
    Not unlike C++ compilers that reload array values into regs whenever a write to
    a similar array happens.
  - 2. Function call reuse. A reused specialization's writes are replayed against borrows, but
    not against flow upgrades (see the flow typing crashes at the top of this file). Since we
    already track free variables, we could simply mark free variables written to, and
    invalidate everything they touch.. that is overly conservative, maybe a more exact system
    can be made.
  The above will generate more issues in code when turned on:
  - For flow upgrades, this can be solved with:
    - You could actually introduce a new hidden variable for each upgrade for the cases
      above where the upgrade gets invalidated due to possible aliasing. This would be
      inefficient because it would introduce a runtime refc++, but if the aliasing is real
      it will not delete the object.
      This of course should not be done for regular invalidations over the same var, which
      are intentional.
    - Alternatively, just let the error happen and the programmer has to re-establish the upgrade.
      This is a bit random, but should generally be super rare.
  - For borrows:
    - Downgrade to a keep automatically in only the cases where alias-invalidates happen, the
      way speculative borrows (FlipSpeculative) and arguments (KeepArgAlive) already are for
      the aliases the checker does see.
    - Could allow it to just be an error, since likely it rarely happens. If it does
      happen it may be a difficult error, but the programmer likely knows they are doing
      some tricky aliasing they may want to simplify?
    - Could allow more explicit borrow annotations.
  If we go this route, should first unify flow upgrades and borrows more, and e.g. allow
  Indexing also in upgrades, and track writes to the indexed expression etc.
  Frankly though, the above is a LOT of complexity, for something that really doesn't ever
  happen.
  Existing examples.
    - Detect this case (as written the caller keeps `b` alive, since `c` is never reassigned so
      it borrows `a` and aliases it; add `c = a` after the `if` and `print b` reads a freed
      object):
        class Test:
            t:Test?
        var a:Test? = Test { Test { Test { Test { nil } } } }
        var c:Test? = a
        def f(b):
            c.t = nil
            print b
        if a.t and a.t.t:
            f(a.t.t)
      - having final/const fields may help reduce the cases where this is an issue.
    - see also: https://nim-lang.org/docs/manual_experimental.html#view-types

- strong typedefs.
  Will basically add a tag to any base type.
  If a functionally specifically requests the tag, the tags must match.
  In any context a type is allowed to lose its tags (coerced to base).
  This way, we can have the few functions that actually want string to contain
  utf-8 take this typedef. Or strings can specify they contain a FlatBuffer
  or some other specific binary layout.
  For scalars and vectors, the tricky thing is that you want some weird
  defaults for operators:
  for +, strong + strong = strong, anything else results in base type.
  for *, strong * base = strong, since you're often scaling a unit.
  It should be possible to override these defaults, disable operators, or
  specify relations with other types, but the default for a type should work
  intuitively for most types (especially spatial quantities, as Lobster is
  game oriented). This overriding is something for later.
  Besides the type system dealing correctly with tags, we now need general
  casts (allow a typedef as function name). We may also need to make string
  constants result in a utf-8 typedef by default.

- A minimalistic error catching feature.
  I'm not a fan of exceptions anymore (though they can be emulated in Lobster in user code),
  and I generally don't think runtime errors should be catchable.
  But functions that bounds-check indices stored in user-generated data such as for reading
  file formats and serialized data break this model, in that you do NOT want user code to
  error/bounds check every single read, yet program terminating upon corrupt data is also
  not that great.
  For that purpose it is maybe useful to have a minimalistic error catching mechanism.
  Since we already have code that rolls back the stack upon an error (and generates an error
  string), we can simply use that code to check if the current function is a function that
  would like to return the error string and continue executing as normal.
  This function must have a return value of type string? (such that nil can mean no error),
  or string if so desired,
  and must somehow be marked as error-catching. If the unroller finds such a function it stops
  unrolling and returns the current error string. The function can also return other strings
  under normal execution.
  We can even provide a function to generate such runtime errors, so that people can abuse it
  as a simple form of (string only) exception handling if they wish.
  Of course can complicate this feature to not make it string only, but I don't think that is
  necessary. If you want to create complex exception hierarchies you are probably using the
  wrong language.
  Might be worth doing at least the initial version of strong typedefs first since that will
  allow a runtime_error string type. Though that tag would have to survive into the vm data.

- Swift's weak pointer feature has some merit.
  It's not a real weak pointer in the sense that it still holds an object alive, more like a
  "2nd class" refc.
  So an object would have 2 refc. If you have the classical cycle, of root -> A, A -> B, and
  B -> A, A would have refc=2 which is the problem. But here, A would have 1 strong, and 1 weak,
  allowing the deallocation to continue. At first strong drops to 0, but weak does not, so it
  is kept alive. Then once the weak also drops to zero it gets deallocated.
  - Note: apparently Swift uses a global hash map to clear backpointers, which is terrible.
  - Also see: Nim is using the annotation .cursor for weak refs.
    https://www.youtube.com/watch?v=aUJcYTnPWCg
  - Vale has good ideas: https://vale.dev/blog/raii-next-steps

Locally Declared Class Members NOTES
====================================
  * `member` works in methods of a class (inline, or a function whose first arg is `x::SomeClass`),
    see docs/source/language_reference.md. What it doesn't do yet is below.
  * A free-standing function with a generic arg, to add state to multiple classes in modular
    fashion:
    def stateful<T>(t::T, ..):
        member track_thing = 0
        // track_thing is now a member of any T this gets called on.
    If needed, allow it without :: also but then it has to be declared as `t.a`.
    It can only be added to T once the caller is being compiled, and by then T may already have
    classes that inherit from it, etc, which would have to be taken into account.
    (Or error if its not a leaf class?)
    Since T is fully specialized by the time the member gets added, it can add it for each specialization
    separately, and since its only used in that specialization there's no need for it to be at the same
    offset as other classes etc, except for sub-class insertion.
    You'd need to check if it already exists (and must have the same type) since two specializations
    of a function that add a member may be called.
    If it was already added in a subclass and now added to the superclass you'd need to move the field
    for all subclasses for this to work!
    If you wanted to simplify you could start with leaf classes since most recipients of these
    members are "environment" style classes that typically are leafs.
    The non-generic free-standing function has the same issue, and errors if the class has
    already been subclassed.
  * what if you want two instances of the state?
    In the case that you're wrapping an `new = f(..., old)` style function, you can do that
    yourself thru naming.
    In the case that you are calling a generic function like stateful<T> above, you can't.
    I guess these are for fairly specialized uses? What's an example of a use where you'd want 2?
  * Since these members are not accessible outside the scope, they are by definition for transient
    uses of data (since you can't even serialize them manually), so should be excluded also in
    any generic serialization/parsing/printing functionality.
  * Scoped member variables that are lifetime bound to the function they're in, added to a specific
    type instead of the type of the first arg:
    def garbage_collect(os:[Object]):
        member visited = false in Object
        // complex recursive algo goes here that marks objects as visited.
        return os.filter(): _.visited
    You can of course do these things with an extra array, but now the array, index, and object
    need to be passed to other functions where in this case just object would suffice.
    Of course you permanently take space in the object, but that could be mitigated by the fact
    that 2 such variables could overlap in storage?
  * Declaring the same member in multiple functions on purpose, to have 2 functions that work on
    the same state (this is a double declaration of the field, and a member is only visible in
    the function declaring it). Of course at some point it becomes better to make an actual class
    but there can be uses for this.
    It is almost like a mixin, and you could imagine it having special syntax to allow groups of
    functions:
    mixin:  // Doesn't need a name, hah!
        a = 1
        def geta(): ..
        def seta(): ..
    However:
    - 90% of uses are likely single function so this syntactic overhead is unwelcome.
    - disallows these functions to be declared in disjoint places.
    - would disallow declaring the var deeper in the method next to where it is actually used.
    - kinda messy that you now need to check both methods for the type to add to, and..
      specialize them both at the same time?? Or add a generic param to the mixin decl somehow?
      This clearly would not work well.


LIFETIME NOTES:
===============
- Ownership ideas the lifetime analysis (see docs/source/memory_management.md) does not do:
  - allow moves into data structures that are not the last use, e.g.
    a := newobject; x.y = a; use(a), since the code after it can be transformed into
    a` := x.y; use(a`)
    Can do the same with push(), i.e. code afterwards becomes a borrow on the last element
    of a vector, which locks the vector as "borrowed from"
  - function return values could borrow if the exp is a field/var reference, if we can
    correlate the parent to a var in the caller (a call to a Lobster function always returns
    an owned value).
  - Would adding non-mutable vectors have any advantages? those could always be consumed by a move.
  - allow the programmer to specify what he wants to happen on a multi-ref: a copy (for non
    mutable / small / stack alloc), an error (for efficient mutables), or an incref (for flexible
    mutables, which is what always happens now).
    We can achieve this with a 3rd kind of type beyond struct / class.. maybe "owned" or "linear"?
    Or make class linear, and have a "reference" or "shared" type.
    Refcounting can then still be had for linear objects thru a level of indirection (a cell
    object referring to a refc object), this way the cost of refc is only paid by these objects,
    and inc/dec can happen at creation/destruction of the cell object.


CURRENT SOLUTION FROM TRADEOFS:
===============================
- We removed co-routines. They're a "sexy" feature everyone always seems
  excited about, but in practice in games they are not all that useful.
  I end up never using them, and when I do, it is for uses that can easily be replaced by
  a class with an update function.
  Having cross-frame state in locals is really not as nice as in member vars.
  It could be cool in complex multi-stage animations.. but even for those it is questionable,
  as code that interrupts/changes these animations then becomes more complex.
  Fundamentally, state that survives a frame needs to be carefully managed regardless.
  Co-routines have also been an endless source of complexity in the VM, and don't fit
  with Lobster's new focus on efficiency.

- decided against:
  - change V_TUPLE into types always being a vector:
    - while it simplifies some cases that currently have to check against V_TUPLE, it
      complicates a ton of code that wants to pass or check a single type.
      Current solution actually rather nice. Also gives nice errors on unexpected use of
      V_TUPLE rather than needing to check that everywhere.
  - use std::variant for nodes in Lobster? or other things like types?
    - std::visit will have horrible performance in debug for that many nodes, also hard to
      debug.
    - nodes can be inline in their parents, total much less allocations.

- namespaces:
  Namespaces use . for both builtins (gl.text) and libraries (gui.text), which is more familiar
  to people, and makes leaving it out more natural.
  A namespace is created by a "namespace gui" declaration, and all top level names get
  automatically prefixed when used outside the namespace.
  Builtins that are only loosely part of a namespace keep _ in their name instead, e.g.
  string_to_unicode / unicode_to_string.
  Could still add optional renaming on import, e.g. import gui as g.

- you can hit multiple overlapping hit boxes with gl.hit(). problem is, you render back to front, but want to hit test front to back...
    - if you simply clear that a hit happened this frame when its tested, you get that order wrong
    - if you added z-layers to rendering such that you could do inverse order
      - if you did it immediate mode, blending wouldn't work correctly, so it would have to be understood that if you did did multiple layers for hit testing, you can't hit on an alpha element
      - could store all render calls and sort (or just reverse) them after, but this is a lot of storing of stuff
        we would store color/blend/transform/shader/texture/linemode for each, which is not that much of an overhead since we set these things on every render op anyway
        (except blend/texture/linemode which can be set when changed),
        so its purely the cost of allocating/storing, and complicating the code a little
    - could track an event handling closure and handle it it at the end of the frame. certainly the simplest, if not totally elegant
      (extra call to handle delayed closure, and delayed closure can't access free variables)
    - you could compare the current hit rect against the last rect that was hit last frame, and if they are the same, this is the one to fire
      problem is, this doesn't work on touch screens, where you lose the first touch down event this way
      -> unless you delayed all touch down events by one frame, to give one hover frame to register (this is the current solution)
    regardless of the solution above, you also need an additional way to cancel hits that happen inside a toolbar or statusbar that may not have hittests everywhere
    -> that can already be done by a gl.hit that doesn't react to it's return value

- for things like GUI callbacks, lobsters non-escaping free var function values kinda suck. options:
  - just call em in place, can only really work in a non-immediate mode gui since otherwise the callback can change the gui layout
    - use hash() of the function value (or text) as element id to make the gui aware of inserts/deletes so this is now safe <- curent solution
      (gui.button_id etc. take an explicit id instead)
      - instead of hashing could have created a vector of args to the gui function as identity. slightly more correct for calls in a loop, but more work.
    - alternatively since all troubles are caused by element insertion/deletion, have special functionality for turning things on/off, i.e. gui_if() instead of if()
  - call em afterwards: problematic because variables not available
  - call em afterwards & force it to take an arg. not elegant, but atleast the arg will remind people to pass values this way
  - implement full closures for escaping situations
    - don't really want another programming language feature just for this
    - to create closure, would need syntax at the call site which is clumsy if it gets forgotten, and some new data structure to hold vars
    - would have to back up old vars, load vars from closure, call function, and put old vars back
    - would probably have a special way to invoke closures so that we don't have to clutter normal function calling, and its easy to give errors if a non-closure is passed in
    - maybe also have a static type for it so no syntax is needed at the call site
